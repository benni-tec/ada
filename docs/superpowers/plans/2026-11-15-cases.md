**Goal:** two new entities beside the models.

- A **case type** defines what a case holds: a schema of fields. "Suspected cancer pathway" is the first.
- A **case** is one instance of a case type, under a **key we set** (so it can point at a record in another system), with its values, its dated step events, and the results of the models that ran on it.
- A **model names one case type**, and the case type's schema must cover what the model needs. Saving a case runs the models on its case type that are set to run automatically; the others run when someone presses Evaluate on the case. Each result is stored on the case, so it can be viewed later.

Cases of a case type are an ADA data source: a wellbeing county can see, per step and over time, how fast its pathways move and whether that improves.

**Why:** Denmark registers every pathway step and monitors the times nationally; Sweden publishes the share within target per region. Finland has no trigger, no clock and no measurement. The pathway model brings the clock to the doctor; the cases bring the measurement to the county.

- **Doctors:** the open cases sorted by deadline status (overdue, due this week, on track), from each case's latest pathway result. Exact; no hazard ratio.
- **Administration:** dashboards per county and step: share within target, median days, the bottleneck step, the trend, and an alert when a step slips.

**Data rule (unchanged):** synthetic data only; the red banner stays. A key is a reference into another system, never a person: a key that looks like a Finnish personal identity code is refused.

**Paths:** `B/` = `services/backend/src/ada/`, `T/` = `services/backend/tests/`, `F/` = `services/frontend/src/`.

## Decisions

1. **A model names its case type, and the schema must cover it.** `StatisticalModel` gains `case_type_id`. A field is `{name, type: text | number | integer | date | boolean | enum | enum_list | day_map, levels?, required, label, help}`. A model's requirement is met when the case type has a field with the same name and type and, for an enum, levels that are a subset of what the model accepts (so a case can never hold a value the model refuses). Creating a model or a new version is refused when a requirement is not met; the error names the field. Extra fields are allowed: saved with the case, in the data source, never passed to a model. A model receives only the fields it declared.
2. **Which models run, and when.** A model has `auto_run` (a bool). On every save of a case, the latest version of every model on its case type with `auto_run` runs. Every model, automatic or not, can be evaluated on a case on request. Results are optional from a data standpoint: a model added later is **never backfilled**; a case has a result from it only once someone evaluates it, or once the case is saved again and the model runs automatically.
2a. **After saving, the case page opens.** The case data first: values (the case type's own fields marked) beside the step timeline, edited in place through a pencil on the card. Beneath it, a table of the models on the case type: runs automatically or on request, the latest result's summary and when, and "View result", or "Evaluate" where there is none. A result opens in a **side sheet** over the page, with the earlier results in a picker and "Evaluate again"; nothing navigates away from the case.
2b. **Models have their own pages.** A list of all models (case type, runs, version, eligible cases, how many have a result) and a page per model with a table of its eligible cases (every case of its case type): key, county, site, latest result, how and when it ran (or "Not run"), filters (all, overdue, open, not run), and the same side sheet per row.
3. **Schemas change compatibly.** A case type has a revision. While it has cases, a change may only add optional fields or add levels to an enum; anything else needs a new case type. Each case records the revision it was last saved under. A change that would leave a model on the case type uncovered is refused.
4. **The key is ours.** `key` is a string set by the caller, unique within the case type, 1–128 characters of `[A-Za-z0-9._:-]`, and never a Finnish personal identity code (`DDMMYY[-+A-FYXWVU]NNN[0-9A-Y]` is refused). Writing a case is an upsert by `(case_type, key)`. The internal id stays for foreign keys; the API addresses cases by key.
5. **Results are history on the case.** Each run stores `{model_id, version, case_revision, section, trigger (auto | request), created_by, created_at}`. Nothing overwrites a result; the latest per model is the one shown.
6. **Events, not only values.** A pathway grows over weeks. A case keeps dated step events (`step, day, recorded_at`); a save appends the events that changed. Values hold the latest state.
7. **Survival never ranks patients.** The open-case list sorts by deadlines only (scheduling). Survival appears in a case's result and in the population view. Ranking by a survival estimate would be clinical prioritisation and a medical device (MDR Rule 11).

## Review Focus

1. **A model names its case type and is covered by it,** at model creation, at each new version and at every case type change; extra fields reach the data source and no model.
2. **Results are history and optional:** a save adds results for the automatic models with the versions used; nothing overwrites one; nothing is backfilled when a model is added.
3. **Keys are ours and never a person:** upsert by key, unique per case type, identity codes refused.
4. **The open-case list never sorts by survival.**
5. **The cases source is an ordinary source:** snapshots, lineage, freshness; dashboards over it carry their lineage to the case type.
6. **Synthetic is said everywhere:** keys, dashboard text, the banner.
